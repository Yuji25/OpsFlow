# OpsFlow

OpsFlow is a cloud-native incident and service operations platform. Phase 1 converts the Session 21 TaskBoard starter into an incident application while keeping its FastAPI, SQLAlchemy, PostgreSQL, Alembic, and React architecture.

## Application

The responsive dashboard supports incident creation, editing, status selection, deletion, status filters, severity badges, and recent incidents ordered by their last update. Loading, empty, and backend-error states include retry support.

Dashboard cards count Open, Investigating, Resolved, and **unresolved Critical** incidents. Resolved incidents never contribute to the Critical count.

Incident fields: `id`, `title`, `description`, `service`, `severity`, `status`, `assignee`, `created_at`, `updated_at`.

- Required: nonblank title (up to 200 characters) and service (up to 120).
- Severity: `LOW`, `MEDIUM` (default), `HIGH`, `CRITICAL`.
- Status: `OPEN` (default), `INVESTIGATING`, `RESOLVED`.
- Description defaults to empty; assignee defaults to `Unassigned` (up to 120 characters).
- UTC creation/modification timestamps are generated by the backend. Modification time changes when details change.

## Run locally

Use a reachable PostgreSQL database and Python 3.12, matching the backend container. Install the existing requirements without changing their versions:

```bash
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export DATABASE_URL='postgresql+psycopg://opsflow:opsflow@localhost:5432/opsflow'
alembic upgrade head
uvicorn app.main:app --reload --port 8000
```

If Python 3.12 is unavailable, use an installed compatible interpreter and record its version. Configuration can also be placed in `backend/.env` using `.env.example`.

In another terminal:

```bash
cd frontend
npm install
npm run dev
```

Open [the dashboard](http://localhost:5173) or [API docs](http://localhost:8000/docs). Vite proxies `/api` to port 8000.

### Docker Compose

Requirements: Docker Engine and Docker Compose with healthcheck dependency support. From the repository root:

```bash
docker compose config
docker compose up --build
```

Open [the Docker-served dashboard](http://localhost:3000) and [Swagger docs](http://localhost:8000/docs). PostgreSQL is published on localhost:5432. Stop the foreground stack with Ctrl+C; `docker compose down` removes containers/network but retains the database volume. Do not use `down -v` on a project containing data you need.

PostgreSQL readiness gates backend startup. The backend runs `alembic upgrade head` before starting Uvicorn; its healthcheck calls `/ready` using Python's standard library. The frontend waits for backend readiness and serves the production Vite build through non-root Nginx on container port 8080, published as port 3000. Its healthcheck uses the image's `wget`; PostgreSQL uses `pg_isready`. The browser's `/api/incidents` requests pass through Nginx to `backend:8000`. No host Vite server or Python environment is needed. The Helm chart below also targets frontend port 8080.

The frontend uses exact dependency versions and a committed lockfile with `npm ci`. Backend dependency versions remain those in `requirements.txt`; no new backend lockfile is introduced. Local environment files/private-key files are excluded from service build contexts. The bundled `opsflow` database credentials are local development defaults, not production credentials.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/` | OpsFlow service/version information |
| GET | `/health` | Liveness (`UP`) |
| GET | `/ready` | Database/table readiness (`READY`) |
| GET | `/metrics` | Prometheus request metrics |
| GET | `/api/incidents` | List incidents, newest ID first |
| GET | `/api/incidents/stats` | Counts: total, open, investigating, critical, resolved |
| GET | `/api/incidents/{id}` | Retrieve an incident |
| POST | `/api/incidents` | Create (201) |
| PUT | `/api/incidents/{id}` | Update supplied fields (200) |
| DELETE | `/api/incidents/{id}` | Delete (204, empty response) |

Missing incidents return 404. Invalid input, including explicit null incident fields, returns 422. Omitted PUT fields remain unchanged. There are no legacy task API aliases.

```bash
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8000/ready
curl -fsS http://localhost:8000/api/incidents/stats
curl -fsS -X POST http://localhost:8000/api/incidents \
  -H 'Content-Type: application/json' \
  -d '{"title":"Checkout errors","service":"checkout-api","severity":"CRITICAL"}'
```

## Database and migrations

`backend/alembic/versions/0001_create_incidents.py` creates the `incidents` table; downgrade drops that table. Run Alembic from `backend/`. The existing backend container still runs migrations before Uvicorn. The starter's startup `create_all` behavior is retained, but migrations remain the supported schema-management path.

**Fresh database required:** the starter task revision has been replaced, not migrated. An existing database stamped with `0001_create_tasks` is incompatible with this new history. Keep any old database/volume intact and provision a separate fresh database (or a separate Compose project/volume). Changing `POSTGRES_*` in Compose does not rename roles/databases inside an initialized volume. No automatic reset or task-record conversion is provided. `alembic downgrade base` deletes incident data; use only on disposable databases when validating migrations.

## CI/CD, GHCR, and Trivy

`.github/workflows/ci.yml` runs on pull requests targeting `main`, pushes to `main`, and manual dispatch. It has three stages:

1. **Validate:** Python 3.12 installs the existing backend requirements and runs `pytest -v` with SQLite isolation; Node 22 runs `npm ci` and the frontend production build. Pip/npm download caches use the dependency files.
2. **Build and scan:** Buildx builds both Docker images locally, with separate build caches and OCI source/revision labels. Trivy scans those exact images before publication. Available table reports are printed and retained for seven days, including on failure.
3. **Publish:** only a successful push/manual run on `refs/heads/main` in `Yuji25/OpsFlow` downloads the scanned images, loads them without rebuilding, logs into GHCR, and pushes them. Image archives are transferred only for eligible runs and retained for one day. PRs never authenticate or publish.

Image references use the full Git commit SHA, with no `latest` tags:

```text
ghcr.io/yuji25/opsflow-backend:<full-commit-sha>
ghcr.io/yuji25/opsflow-frontend:<full-commit-sha>
```

Repository owners are normalized to lowercase. The workflow defaults to `contents: read`; only the guarded publication job has `packages: write`. GHCR login uses `github.actor` and the built-in `GITHUB_TOKEN`, with no custom PAT. The write-enabled job does not check out or execute application code. No Docker Hub publication or deployment is configured.

### Blocking security gate

The rubric explicitly requires failure on HIGH or CRITICAL CVEs. Trivy v0.70.0 scans OS and application dependencies with `scanners: vuln`, `severity: HIGH,CRITICAL`, `ignore-unfixed: false`, and `exit-code: 1`. Neither scan uses `continue-on-error`. The frontend scan still runs if the backend scan fails; findings or scanner errors fail the stage and prevent publication. Report upload never turns a failed scan into success.

The Trivy action is pinned to the verified v0.36.0 release commit; the other actions use verified release majors. No CVE exceptions or informational-only bypasses are provided. Existing base-image/dependency CVEs may make the first run red: review the reports and address findings separately instead of weakening the gate to obtain a green run. A clean report is limited to the selected severities and the scanner's vulnerability database at scan time.

### GitHub setup and grading evidence

After committing/pushing manually, enable Actions and allow the referenced GitHub, Docker, and Aqua actions if repository policy restricts them. Existing GHCR packages must grant this repository Actions write access; newly published packages should link to the repository through workflow publication and their OCI source label. Confirm package visibility manually; set it to public if graders need anonymous pulls. Do not add a PAT merely to bypass a package-access configuration problem.

Verify that a PR validates/builds/scans and skips publication. On main, verify all three jobs and both package pushes, then pull each SHA-tagged image. Manual dispatch on another branch must not publish. Publication of the two packages is sequential, not an atomic release; a registry failure may leave one image published while the job fails.

Capture actual evidence only:

- Backend `pytest -v` output and frontend build output.
- Both Trivy report tables (including severity, package, CVE, and fixed-version columns), or clean results.
- Both GHCR package pages showing full-SHA tags and the linked OpsFlow repository.
- A PR run showing publication skipped.

For the rubric's short security explanation, describe the image/package and CVE, severity and affected/fixed versions from the real report, and the remediation. If clean, explain what Trivy scanned and the result's time/severity limits. Do not claim a successful Actions run or fabricate screenshots before the workflow actually runs.

## Kubernetes / Helm on Minikube

Requirements: Docker, Minikube, kubectl, Helm 3, and sufficient free host memory for the existing Minikube profile. This local deployment uses the public, CI-scanned application images at commit `1fed766228c47ca4bd25f12a8c86128199dbdd14`; no `latest` tag or registry credentials are needed.

```bash
minikube -p minikube start
minikube -p minikube addons enable ingress
minikube -p minikube addons enable metrics-server
kubectl --context minikube apply -f k8s/namespace.yaml
helm lint helm/opsflow -f helm/opsflow/values-minikube.yaml
helm template opsflow helm/opsflow -n opsflow -f helm/opsflow/values-minikube.yaml
helm upgrade --install opsflow helm/opsflow --kube-context minikube -n opsflow \
  -f helm/opsflow/values-minikube.yaml --wait --wait-for-jobs --timeout 10m
kubectl --context minikube get pods,svc,ingress,pvc,hpa -n opsflow
helm list --kube-context minikube -n opsflow
```

The chart uses the release namespace; `k8s/namespace.yaml` creates the local `opsflow` namespace separately. PostgreSQL has a 2 GiB persistent volume and a single replica with a Recreate strategy. The bundled credentials are **local demonstration defaults only** and are stored in a Kubernetes Secret. Changing values does not change credentials in an already initialized database. Do not use these defaults for a cloud deployment.

Each Helm revision creates one migration Job, which waits for PostgreSQL and runs `alembic upgrade head`. It is an ordinary Job rather than a pre-install hook, so the first install can create PostgreSQL before migrations run. Backend init containers only check that the database is at the image's expected Alembic head; they do not execute migrations. Helm overrides the backend image command with Uvicorn to avoid the image's usual per-container Alembic step. The Docker image and Compose startup behavior remain unchanged. `--wait --wait-for-jobs` checks both workloads and the migration Job; a failed migration fails deployment validation. Finished Jobs expire after ten minutes.

The frontend has two replicas. The backend HPA maintains two to four replicas at a 70% CPU target, with a 100m CPU request per backend pod. Metrics-server must be available; allow time for its first numeric sample. Both application containers retain their non-root users. ClusterIP Services expose backend port 8000 and frontend port 80, targeting container ports 8000 and 8080. The backend Service is deliberately named `backend` because the published frontend Nginx configuration proxies to `backend:8000`; use one OpsFlow release per namespace.

Ingress uses class `nginx` and host `opsflow.local`: `/api` and `/docs` route to the backend; exact `/health`, `/ready`, `/metrics`, and `/openapi.json` routes expose operational endpoints and Swagger's schema. `/` routes to the frontend, retaining its SPA fallback. These unauthenticated operational routes are for the local demonstration and should be reviewed before cloud exposure.

On Linux with a reachable Minikube Docker IP:

```bash
minikube -p minikube ip
curl --noproxy '*' --resolve "opsflow.local:80:$(minikube -p minikube ip)" http://opsflow.local/health
curl --noproxy '*' --resolve "opsflow.local:80:$(minikube -p minikube ip)" http://opsflow.local/ready
curl --noproxy '*' --resolve "opsflow.local:80:$(minikube -p minikube ip)" http://opsflow.local/api/incidents/stats
kubectl --context minikube top pods -n opsflow
kubectl --context minikube get hpa -n opsflow
```

For browser access, manually map the reported Minikube IP to `opsflow.local` in your hosts file, then open `http://opsflow.local` and `http://opsflow.local/docs`. If that IP is unreachable on your platform, forward the ingress controller and map the hostname to `127.0.0.1` instead:

```bash
kubectl --context minikube -n ingress-nginx port-forward svc/ingress-nginx-controller 18080:80
# Then open http://opsflow.local:18080 with opsflow.local mapped to 127.0.0.1.
```

Verify create/edit/delete through the dashboard, operational endpoints, numeric HPA metrics, and at least two Ready pods per application Deployment. Repeat the same `helm upgrade --install` command to verify an upgrade; existing incidents and the PostgreSQL PVC should remain. Capture real pods, Services, Ingress, HPA, Helm release, and browser output manually. A completed migration pod is expected until its Job expires; the five long-running application/database pods must be Running and Ready.

Keep the release running for review. The database PVC has `helm.sh/resource-policy: keep` to retain data on uninstall. Do not delete the PVC, namespace, Minikube cluster, or Docker volumes as a routine validation step; those actions can destroy data. No monitoring stack or ServiceMonitor is installed by this chart.

## Prometheus / Grafana on Minikube

Phase 6 uses standalone charts in `opsflow-monitoring`: `prometheus-community/prometheus` **29.36.1** (Prometheus v3.15.0) and `grafana-community/grafana` **13.5.0** (Grafana 13.2.3). These are local demonstration installations. Recheck available host memory first; allow at least 3 GiB available before installing. No Operator, ServiceMonitor, application chart changes, or additional Ingress routes are needed.

From the repository root, with the existing Minikube and OpsFlow release running:

```bash
free -h
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo add grafana-community https://grafana-community.github.io/helm-charts
helm repo update
kubectl --context minikube create namespace opsflow-monitoring --dry-run=client -o yaml | kubectl --context minikube apply -f -
kubectl --context minikube -n opsflow-monitoring create configmap opsflow-dashboard \
  --from-file=opsflow-dashboard.json=monitoring/opsflow-dashboard.json \
  --dry-run=client -o yaml | kubectl --context minikube apply -f -
helm upgrade --install opsflow-prometheus prometheus-community/prometheus \
  --version 29.36.1 --kube-context minikube -n opsflow-monitoring \
  -f monitoring/prometheus-values.yaml --wait --timeout 10m
helm upgrade --install opsflow-grafana grafana-community/grafana \
  --version 13.5.0 --kube-context minikube -n opsflow-monitoring \
  -f monitoring/grafana-values.yaml --wait --timeout 10m
kubectl --context minikube -n opsflow-monitoring get pods,svc,pvc
helm --kube-context minikube list -n opsflow-monitoring
```

Prometheus discovers Ready `opsflow` backend pods on port 8000 and scrapes each replica's `/metrics` every 15 seconds. Targets carry `job="opsflow-backend"`, `namespace="opsflow"`, `pod`, and distinct `instance` IP:port labels, including new replicas created by HPA. The chart creates a read-only discovery ClusterRole and binds it to the Prometheus service account. Verify cross-namespace access explicitly:

```bash
kubectl --context minikube auth can-i list pods -n opsflow --as=system:serviceaccount:opsflow-monitoring:opsflow-prometheus
kubectl --context minikube auth can-i watch pods -n opsflow --as=system:serviceaccount:opsflow-monitoring:opsflow-prometheus
```

Only Prometheus self-scraping and the application job are enabled. Alertmanager, Pushgateway, node-exporter, and kube-state-metrics are disabled. Prometheus requests 256 MiB and is limited to 768 MiB; its config reloader requests 16 MiB and is limited to 64 MiB. Grafana requests 128 MiB and is limited to 512 MiB, with no discovery sidecars or cluster RBAC. Prometheus stores up to six hours of samples with a 512 MB retention-size target on a retained 2 GiB PVC. Its Recreate strategy avoids concurrent writers during an upgrade.

In separate terminals, forward the services to localhost only:

```bash
kubectl --context minikube -n opsflow-monitoring port-forward svc/opsflow-prometheus 9090:80
kubectl --context minikube -n opsflow-monitoring port-forward svc/opsflow-grafana 3001:80
```

Open [Prometheus](http://localhost:9090) and [Grafana](http://localhost:3001). Grafana uses username `admin`; retrieve its chart-generated password locally (never paste it into Git, logs, screenshots, or this README):

```bash
kubectl --context minikube -n opsflow-monitoring get secret opsflow-grafana -o jsonpath='{.data.admin-password}' | base64 --decode
```

Anonymous Grafana access is disabled. These services and credentials are for the local classroom deployment; no public exposure is configured. The default **OpsFlow Prometheus** datasource and **OpsFlow / OpsFlow Operations** dashboard are provisioned automatically. No manual dashboard creation, import, or datasource setup is required. The committed JSON is mounted through `opsflow-dashboard`; rerun the ConfigMap command after changing it and allow ten seconds for provisioning.

The seven panels show backend scrape targets UP; incident API request rate; request increase over the selected period; method/status-class breakdown; mean latency by handler; and process CPU/memory by backend pod. All queries use actual backend metrics: `http_requests_total`, `http_request_duration_seconds_sum/count`, `process_cpu_seconds_total`, and `process_resident_memory_bytes`. Status labels are `2xx`/`4xx`/`5xx`, not exact response codes. API panels exclude health/readiness/scrape requests. Windowed increases can be fractional; latency can have gaps when no requests occur. Process CPU/memory are not total Kubernetes pod usage. No unavailable incident-count or pod-resource metrics are invented.

Validation, with the port-forwards running:

```bash
curl -fsS 'http://localhost:9090/api/v1/targets?state=active'
curl -fsSG http://localhost:9090/api/v1/query --data-urlencode 'query=up{job="opsflow-backend"}'
curl -fsSG http://localhost:9090/api/v1/query --data-urlencode 'query=sum(http_requests_total{job="opsflow-backend",handler=~"/api/.*"})'
```

The application job should show both backend replicas independently UP. Generate real create/edit/delete activity through `http://opsflow.local`, wait for at least two scrapes, and inspect the dashboard over the last 15 minutes with 15-second refresh. If values have not updated, use the dashboard Refresh button and confirm the scrape time has advanced. A 404 or invalid request can demonstrate real 4xx traffic; do not fabricate 5xx errors or synthetic metric values. Verify the datasource with Grafana's health check and confirm panels change with traffic. Capture actual `/metrics`, Prometheus Targets, and populated dashboard evidence manually after review.

Repeat both pinned Helm upgrade commands to validate upgrades. For restart validation, restart only the two monitoring Deployments and wait for rollout; reconnect port-forwards if their selected pods were replaced and retrieve the current Grafana Secret after an upgrade. Prometheus samples persist on its PVC. Grafana storage is deliberately ephemeral: its datasource/dashboard are restored from committed provisioning files, while UI-only changes and sessions are disposable. Leave both releases running for review. Do not delete namespaces, PVCs, OpsFlow resources, Docker volumes, or other projects during validation.
